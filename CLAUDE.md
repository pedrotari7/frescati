# Frescati

Mobile-first PWA for running a recurring football group. A **season** defines a repeating slot (e.g. every Tuesday 19:00 at Frescati IP) and a date range; **games** are generated from it; players report **In / Out** for each game.

## UI Changes

- Mobile is the primary target. Design for a phone first, then make sure it still works on desktop.
- All UI changes must be responsive — always consider both mobile and desktop layouts across multiple screen dimensions.
- The app is permanently dark. Colours come from the CSS variables declared in `frontend/app/globals.css` (`@theme`) — never hardcode hex values in components.

## Running the app

- Do not start a dev server or run the app yourself. If you need to verify behavior, ask the user to check it (the user typically already has it running locally).
- **`pnpm test:e2e` is the exception, and it is the recommended way to check a journey end to end.** It is a test command, not a dev server: Playwright's `webServer` runs `pnpm dev:e2e` — `scripts/e2e-stack.sh`, which starts a production `next build` in the background, compiles the backend, then boots every emulator, seeds a real scenario, waits out whatever is left of that build and serves it with `next start`. The whole thing is torn down on exit. Run it rather than pushing and waiting on CI. Things to know before starting one — **check port 3000 is free first**, because `reuseExistingServer: !CI` means an already-running `dev:seeded` gets silently reused, skipping the fresh seed and pointing the tests at the user's live working data; a clean run **wipes and reseeds the emulators** and rewrites `frontend/public/dev-users.json`; and `--project=mobile` is the quick first pass. Teardown does not always take the Firestore emulator with it — the `java` process can outlive the run still holding 8080, and the next run dies with "Could not start Firestore Emulator, port taken". Check the port before blaming the change you just made.
- **It serves the built app, not `next dev`, and that is load-bearing twice over.** `next dev` compiled each route the first time a test opened it, so the suite stalled in front of every screen it visited and then re-rendered each one through webpack's eval'd modules — about as long compiling as testing. It is also the more honest thing to run: `next.config.js` says out loud that a dev server is a materially different app from the one that ships, and this is the one suite whose job is to check the halves meet. The catch is that a faster app finds races the slow one hid — the kit handover test picked a squad member **by position** out of a list that re-sorts when the profiles subscription lands, and started handing the ball to whoever sorted first. Anything reading a name out of a list and then clicking it has to click **that person**, not that row.
- **The three spec files run in parallel and the two viewports do not.** `workers: 3` with `fullyParallel: false` gives each file a worker and keeps the tests inside it in order, which is what they expect — they hand state to each other on purpose. The files themselves are disjoint (responses on the next game, the kit register, the scoreline and vote on a played one), so they can overlap. The viewports cannot: they run the *same* specs against the *same* seeded database, so `desktop` declares `dependencies: ['mobile']`. Two consequences — asking for `--project=desktop` runs mobile first, and a red mobile leaves desktop reported as never run.
- `pnpm dev:seeded` is the whole local stack in one command (emulators + seed + dev server); `pnpm dev:live` is the same against the real project. Both set `NEXT_PUBLIC_USE_EMULATORS` themselves, so `frontend/.env.local` should be left alone.
- Local data comes from `pnpm seed`, which fills the running emulators from a scenario in `backend/scripts/seed/scenarios.ts`. Nothing is mocked — real rules, real triggers. Adding a case worth looking at means adding a season or a `pins` entry there, not writing Firestore by hand.
- The seeder derives everything it can from `shared/` (`tallyResponses`, `pickTeams`, `getStandings`, `getRatingChanges`) so seeded data is exactly what the functions would have produced. Only scorelines are invented. Keep it that way — a hand-written rating column disagrees with the first replay.
- Seeded seasons carry a per-run id suffix. Deleting a season fires a cascade that can still be running a minute later, and stable ids meant it deleted the next seed's data.
- `NEXT_PUBLIC_USE_EMULATORS=1` also turns on the dev user switcher (`DevUserSwitcher`), which signs in as any seeded player without Google.

## Local environment gotchas

- The shell exports an `npm_config_registry` pointing at Spotify's artifactory, which overrides `.npmrc`. Prefix installs with `npm_config_registry=https://registry.npmjs.org/`.
- `firebase-tools` needs **JDK 21+** and the default `java` here is 17. `scripts/emulators.sh` finds a newer one, and every emulator script goes through it — so no `JAVA_HOME` prefix is needed. A raw `firebase emulators:*` still does.
- `pnpm seed` **transpiles rather than typechecks** (`ts-node --transpile-only`), because it sits in front of every `dev:seeded` and every e2e run and `backend/tsconfig.json` excludes `scripts/` from the build. `pnpm --filter backend typecheck:scripts` is where `backend/scripts` gets checked, once, in the backend CI job — the other scripts there still run through a checking `ts-node`, since nobody is waiting on a backfill.
- `pnpm test` runs the pure `shared/` suites **and nothing else** — green there says nothing about the frontend, the rules or the functions. `pnpm test:all` runs all four; it needs ports 8080/9099, so stop `dev:seeded` first. It does **not** include `pnpm test:e2e`, which is deliberately separate because it starts and stops its own stack — see "Running the app". `pnpm test:rules` after **any** change to `firestore.rules`, `pnpm test:backend` after any change under `backend/src`.

## Architecture

- **pnpm workspace**, one lockfile at the root. Packages: `frontend`, `backend`. `shared/` is a plain TS directory (no `package.json`) compiled into both — imported as `@shared/*` in the frontend and `../../shared/*` in the backend.
- **Frontend**: Next.js 15 App Router on Vercel. Reads and writes Firestore **directly** from the client; security rules are the authorization layer. Realtime everywhere via `onSnapshot`.
- **Backend**: Firebase Cloud Functions v2 (`nodejs24`, `europe-west1`). Only privileged work lives here — response counters, push notifications, scheduled reminders, admin claims. There is **no API layer**; do not add one without a reason. The single route handler, `app/api/csp-report`, is not one: it logs a browser's CSP violation report and answers 204, reading and authorizing nothing.
- **Auth**: Google popup only. `admin` is a Firebase custom claim (global app admin). Per-season admins are `adminUids` on the season doc.
- **Anyone signed in can read everything** — there is no allowlist and no approval step, deliberately, because extras have to be able to find a game and put their hand up. Don't "fix" it without reading "Who can see the group" in the README first; the trade-offs are written down there. Two things are held back regardless: email addresses (Firebase Auth only) and push tokens (private to their owner).
- **App Check** attests requests come from the real app rather than a script holding the same public config. Every route into Firebase goes through `frontend/lib/firebaseClient.ts`, which starts it lazily — that is why `app` is not exported and `getFirebaseApp()` is, so nothing can reach a service without it.

## Data model

```
users/{uid}                                  profile + notificationPrefs + client + rating (function-owned)
users/{uid}/pushTokens/{token}               FCM registration tokens — private to their owner
seasons/{seasonId}                           slot, venue, minPlayers, balance, memberUids[], adminUids[]
seasons/{seasonId}/kit/{itemId}              a ball, the vests — name, kind, holderUid
seasons/{seasonId}/games/{gameId}            kickoff, status, counts (function-owned), atRisk
seasons/{seasonId}/games/{gameId}/responses/{uid}   status: 'in'|'out', role: 'member'|'extra', absent?
seasons/{seasonId}/games/{gameId}/watchers/{uid}    following this game — private to its owner
seasons/{seasonId}/games/{gameId}/tournament/teams  generated lineup (function-owned)
seasons/{seasonId}/games/{gameId}/tournament/result confirmed table + rating deltas (function-owned)
seasons/{seasonId}/games/{gameId}/tournament/motm   counted man-of-the-match vote (function-owned)
seasons/{seasonId}/games/{gameId}/motmVotes/{uid}   one vote — private to its owner
seasons/{seasonId}/games/{gameId}/matches/{order}   one scoreline; doc id is the fixture order
ratingLedger/{gameId}                        one entry per rated game (function-owned)
```

**No response document at all means "no response"** — that is a real third state, not a default. Never write a placeholder response doc.

`counts` and `atRisk` on the game doc are written **only** by the `onResponseWrite` Cloud Function. Security rules reject client writes to them. Don't compute them on the client.

## Tournaments

Games of 8+ split into 2, 3 or 4 teams (`shared/tournament.ts`) and play a generated round robin. Squads differ by at most one player; the on-pitch side size is the smaller of the two squads meeting, with the larger rotating a sub through.

- **Ratings** are a global career Elo on `users/{uid}.rating`, shown as 0–100 via a fixed mapping (`shared/rating.ts`). A rating moves on how a team finished _versus how it was expected to_, not on raw position — with a working balancer, raw position is nearly noise. Unrated players seed at the live average of the season's rated members.
- A **starting rating** is an app admin's estimate of somebody who hasn't played yet, set from `/admin/ratings` through the `setStartingRating` callable. It stores a real rating on `games: 0`, so `hasPlayed` rather than the presence of the field is what "the ladder has had its say" means — the balancer uses it from their first game, the all-time ladder leaves them off, and the provisional K-factor still moves them fast. **Only settable before their first rated game**, and not by taste: every ledger entry records what each player carried into that game, so overwriting an earned rating would be silently undone by the next replay. Fix an earned rating by fixing the scores behind it.
- **Teams** are picked by the pure, seeded `pickTeams` in `shared/optimizer.ts` and written **only** by the `rebuildTeams` function. Rules reject every client write to the teams doc — an admin reshuffles by bumping `reshuffleCount` on the game, never by writing a lineup.
- Rebuilds are **debounced through Cloud Tasks**: a response write bumps `teamsGeneration`, queues a task carrying it, and the handler drops itself if the generation has moved on. Kept out of `onResponseWrite` deliberately — the optimizer is the one part of the app whose cost grows with turnout. Cloud Tasks has no emulator, so locally `enqueueTeamRebuild` runs `runTeamRebuild` in-process instead. A confirmed game's lineup is never rebuilt — the ledger was computed against it and a replay reads it back.
- **An admin can move people by hand, and doing so pins the lineup.** `setPlayerTeam` is the one door out of an automatic team sheet, for the Tuesday where two of the eleven who said In are still on a bus and somebody's brother has turned up in boots — it moves a player between squads, off the sheet (`teamIndex: null`) or back onto one, all of which are the same write in `shared/lineup.ts`. Still a callable rather than a loosened rule, for the reason the rules file gives: `tournament/teams` is writable by nobody at all, which is what stops a player putting themselves on the side they fancy — and the checks it makes (a squad that can't be emptied, a player who has to be in the pool the optimizer picks from) are ones CEL can't express against a list of maps anyway. What it writes is `edited`, and **its presence is the pin**: from then on `runTeamRebuild` leaves the sheet alone, because the next person to change their mind must not silently undo the evening's planning from a screen nobody is looking at. **Reshuffle is the way back** — that button already means "re-pick these teams", so `onGameWrite` queues its rebuild with `force`. The price of pinning is that the sheet and the pool can drift apart in both directions, so the screen says so rather than hiding it: whoever is In and on no team gets a panel of their own, and whoever is on a squad and has since tapped Out is struck through on it. An automatic lineup needs neither said, because a rebuild is already seconds away.
- **Scores** live at `matches/{order}` where the id is the fixture's place in the running order, so two people scoring the same match write the same document. **No match document means "not played"** — same third state as a response, and for the same reason.
- Anyone holding a response on the game can write a score. Confirming the game (`resultFinalisedAt`) closes it to everyone but a season admin, whose correction triggers a **replay**: `replayRatingsFrom` rewinds the ledger latest-first and replays it in kickoff order. Adjusting only the corrected game would be wrong, because every game after it was rated against the ratings that game produced.
- Ratings apply on an admin's Confirm, or automatically `AUTO_FINALISE_HOURS` after kickoff via `finaliseDueTournaments`.
- **Man of the match is the one thing the ladder cannot work out for itself**, so it is put to the people who were there. Confirming a game opens the vote (`motmVotingUntilMillis` on the game) and notifies the lineup; `closeMotmVoting` counts it `MOTM_VOTING_HOURS` later, writes `tournament/motm`, tells the same people how it went and **deletes the window** — which is what takes the game out of that sweep's single-field query for good, and what shuts the rules. Only players in the lineup may vote, and only for one; voting for yourself is allowed on purpose. **Votes are private to their owner**, admins included, and that is load-bearing rather than tidy: a running count visible while the vote is open turns an early lead into a bandwagon. The totals are published with the decision.
- **The turnout is published while the vote runs; the tally is not.** `onMotmVoteWrite` re-derives `tournament/motmVoters` — uids and nothing else — so the panel can say who has answered and who still needs asking. That is not a hole in the rule above but the other side of it: eight names with no picks attached give nobody a lead to fall in behind, which is the only thing that rule exists to prevent. It is function-written for the same reason `counts` is, that no client can read anybody else's vote to work it out, and `closeMotmVote` **deletes it with the window** — from then on the turnout is the sum of the published counts, and a second copy would be one to keep in step. The one disclosure to accept is at the tail: with a turnout of one, knowing who voted and reading the totals afterwards identifies their pick.
- **An open vote holds a game on the season's home screen.** `groupGames` in `shared/game.ts` splits the calendar into four — the next game, what's coming up, what is still being voted on, and what's played — and a finished game only reaches the last of those once its window is gone. The Played list is collapsed by default, which is where a two-day vote goes to be missed. The window is the whole test, so a game nobody confirmed is archived from the final whistle exactly as before, and one whose votes have been counted drops in on its own with no state to keep in step. It never takes the top card off the next game, and the row it draws links to the team sheet where the vote actually is — the same place the notification lands.
- The bonus reaches a rating **through a replay**, never a poke. `computeGameRatings` reads the decision document back and `applyMotmBonus` adds it, so closing a vote asks for `requestRatingReplay` like a corrected scoreline does — for the same reason, that every game rated afterwards was rated against what this one produced. Anything applied in place would be erased by the next correction. It is **zero-sum**: the pot is funded by everybody who played, winner included, because the displayed 0–100 is mapped from a fixed Elo span and a bonus minted weekly would drift the whole group up it. A tie splits the pot rather than the coin, like `getActualWins`.
- **A player's record** (`/u/[uid]`) is aggregated from the ledger and nothing else — `shared/player.ts`. Appearances, wins, runs, who they play with and the rating line all come off the same entries the table reads, so a correction that replays the ladder fixes the profile in the same pass and nothing can drift. It says how a team _placed_, never "2nd of 4": with a tie for last place the number of teams isn't recoverable from `positions`. The query filters on `positions.{uid}` and rides Firestore's automatic map-subfield indexes — no composite index, no mirrored `uids` array, and **no single-field exemption on `positions`**, which would silently break it.
- **`positions` says where a team finished; `teams` says who was on it.** They look interchangeable and are not: `positions` is a competition ranking shared on a tie, so a two-team game that ends level puts the whole lineup on 0 and every player looks like everybody's teammate. `getPlayerLinks` needs the team index, which is why `computeGameRatings` writes `teams` onto the entry — denormalised for the same reason the rest of it is, so a career screen reads one collection rather than one team sheet per game. It is **optional**, like `motm?`: entries rated before the field existed have none, `getPlayerLinks` **skips** those rather than guessing, and the panel says how many games it actually read so a thin answer doesn't look like a complete one. `backfill-ledger-teams` fills them in from the team sheet — safe years later precisely because a confirmed game's lineup is never rebuilt — and reports rather than repairs when a sheet is missing or names a different squad than the entry rated.
- **`before: null` says a player carried no rating in; `seedElo` says what the game rated them off anyway.** Those are different facts and one field cannot hold both. `before` exists so a rewind can restore *nothing*, which is what an unrated player had, and it has to keep meaning exactly that — but the game did not treat them as nothing, it seeded them at the live average of the season's rated members and moved them from there. Without the seed on the entry, every screen aggregating the ledger has to score a first appearance as **no movement at all**, so a newcomer sat on 0 in the season table while the ten people they played with showed the same ninety minutes as ±4. One number per entry, because it is one number — everybody unrated in a game seeds at the same average. **Optional, like `teams?`**: left off entirely when nobody was unrated, since there was no seed to record; absent on entries written before it existed, where `getSeasonTable` and `getPlayerGames` fall back to counting nothing because the distance genuinely isn't recoverable. `backfill-ledger-seed` fills those in from `tournament/result.changes[].before`, which is the seed the game actually used, written by the same call that wrote the entry — and skips a game whose result is gone rather than guessing. A replay writes it too, so a corrected scoreline fixes historic entries in the same pass.

## Reporting a no-show

- **`absent` on a response says they said In and didn't turn up.** A mark *beside* the answer rather than a change to it, and that is the whole design: `status` still says `in`, because that is what they said, and this says the pitch disagreed. Rewriting them to `out` would file a no-show under the same heading as somebody who had the courtesy to say so, which is precisely the distinction anybody asking wants. `isAbsent` in `shared/game.ts` is the pair read together, so a mark left on somebody who later changed their answer can never make an `out` read as a no-show.
- **Only from kick-off**, which `canReportAbsence` decides. Before then "they haven't turned up" describes everybody including the eight people parking, and an admin handed the button on a Sunday would be reporting a prediction. It stays available past the final whistle, because this is remembered rather than recorded on the spot.
- **It moves nothing else.** Not `counts`, which describes what people answered; not the lineup, which by then is whatever the admin has decided it is; not a rating. That is not an omission — by the time this can be written, the headcount has stopped being a decision anybody is making, and re-picking the teams at five past seven because somebody is on a bus is the opposite of what the person holding the phone wants. A squad that is genuinely a man down is rebalanced with `setPlayerTeam`, which is a separate decision and one tap away. The consequence to accept is that a no-show left on the team sheet is still rated with their team; moving them off it before the game is confirmed is how you keep them out of the ledger, and after it the lineup is frozen either way.
- **Season admins only, and frozen against the player it is about.** The rules refuse it on a self create like `confirmOverride`, and *freeze* it on a self update — because changing your mind rewrites the whole document, so without that a no-show could clear the mark by tapping Out and In again. It is on the `responseShapeOk` allowlist anyway so `setResponse` can carry an admin's mark through untouched; a key it may not send is a key it cannot preserve, and dropping it would deny the honest answer change rather than quietly losing the mark. Unsigned, unlike a scoreline or a kit handover: those are writable by anybody who turned up, so a wrong one needs a face, and this one is writable only by the people the season document already names.
- It shows in two places, and neither is subtle. The roster lifts a no-show out of the group they answered into and into a **section of its own** — left among the people who turned up, marked, it reads as a footnote. The **team sheet** strikes them through, because that is the one screen in a position to say which squad played a man short.

## Kit

- A season keeps a **register** of what the group owns — `seasons/{id}/kit/{itemId}`, one document per ball or set of vests, at `/s/[seasonId]/kit` behind the Squad tab. The only question it answers is *who has it*, which is why `holderUid` is **required**: an item nobody holds is the situation the register exists to prevent, and making it a state you could save would legitimise it. Kit in a cupboard is still somebody's to fetch.
- **Whether a game has a ball is derived, never stored.** `getKitStatus` in `shared/kit.ts` reads the register against that game's responses, both of which the client already holds. There is no counter and no trigger behind one — `counts` needs a function because a client can't read everybody else's response to tally it, and this needs nothing of the sort. A field that could drift, plus a sweep to notice it had, is machinery bought for a question two arrays answer.
- A kind is covered when **any one** item of it is held by somebody who said In. That grouping is the whole reason `KitKind` is a closed set rather than a typed label: a game needs *a* ball, not every ball, so two items have to be interchangeable before either counts as cover — and "Ball", "ball" and "Match ball" would be three kinds. `other` is the escape hatch for a pump or a gate key, tracked but never warned about, because a register that cried wolf about the pump is one nobody reads in the week it matters.
- **A gap is only ever reported against kit the group owns.** A season with no vests in the register isn't short of vests, it's a group that plays skins versus shirts. You can only be missing something you have.
- **`unknown` is the third state**, for the same reason a missing response document is: somebody who hasn't answered hasn't said no. `missing` is a handover to arrange today and `unknown` is a person to chase, and a warning that shouted NO BALL every week until the holder happened to tap In would be wrong more often than right.
- The test is `status === 'in'`, pointedly **not** `isConfirmed`. Confirmation decides whether an extra counts towards the headcount; it says nothing about whether the bag in their hallway is coming.
- **Any member can hand any item to any other member** — the same bargain the scoreboard strikes, because a handover happens at a pitch between two people and routing it through an admin means it never gets recorded at all. What they can't do is change what an item *is*: naming, re-kinding, adding and deleting stay with season admins, since a member who could re-kind the vests as `other` could silence that warning for the whole squad. The rules express that as a diff — a member's write may touch `holderUid`, `updatedBy` and `updatedAt` and nothing else.
- The holder is checked against `memberUids` **on the way in only** — a write that leaves `holderUid` where it is skips the check entirely — so a roster that moves underneath a register strands whatever the departing member held. Applied to every write instead, it stopped being a check on handovers and became a freeze on the document: an admin couldn't correct the name of the one item the register was actively complaining about until they had first invented a holder for it. `findStrandedKit` **reports without repairing**, the same bargain `findCountsDrift` strikes: the app has no idea who has the ball now, and quietly reassigning it to the nearest admin replaces a visible problem with an invisible wrong answer. `forget-player` says so in its plan rather than guessing.
- The compact strip on the next-game card **draws nothing when everything is covered**. That card is the one screen most people ever look at, and a green tick confirming the ball exists is not what they opened the app for.
- No backend at all: `onSeasonDeleted`'s `recursiveDelete` already takes the subcollection, and nothing here needs privilege.

## Notifications

- A push reaches somebody only if all three line up: a **registered device**, the **preference** for that kind switched on, and — on iPhone only — the app **installed** to the home screen, which is the one Safari allows push from at all. `getPushReach` in `shared/notifications.ts` is that rule in one place; a missing preference means opted in, matching `resolveRecipients` on the backend.
- **`availability` is the one kind with no profile switch**, and `NOTIFICATION_PREF` maps it to `null` to say so. Every other notification goes to a standing audience nobody signed up for — the season roster, everyone who answered, every app admin — so the profile is the only place to say no. This one goes only to whoever tapped the bell on one game, off by default, and unfollowing is the switch. A second one on `NotificationPrefs` would be a setting that means nothing until you have already opted in somewhere else, the same reason `relevantPrefs` hides `newPlayers` from everybody but an admin. `null` skips the **kind** check only: `emailFallback` still applies, because that picks a channel rather than a kind.
- **`motm` carries its own preference** rather than borrowing `reminders`. It goes to a standing audience — everybody in the lineup — which is the test that decides whether a kind needs a profile switch at all, and muting the chase for an answer says nothing about wanting to be asked who played well. It is one of the two kinds sent *after* the football, which is why `buildGamePush` makes `respondable` kind-aware off an `AFTER_THE_GAME` list rather than a `!== 'motm'`: the worker's "I'm in" shortcut would open the app and do nothing. `finaliseTournament` and `finaliseDueTournaments` therefore declare `EMAIL_SECRETS`, without which its fallback would silently mail nobody.
- **`motmResult` is the other half of that exchange, and it shares the question's switch.** A group interrupted to answer something and never told the outcome is a group that stops answering, and until this went in the result reached only whoever happened to open the app again. It is the one thing the app sends that is purely news — nothing to answer, nobody to bring a ball. The audience is the **lineup, not the voters**: somebody who never got round to voting still played, and scoping it to people who answered would quietly make the notification a reward for having answered. It stays on `motm` rather than earning a switch of its own, which by the rule above it would otherwise qualify for — it goes to *the same* standing audience about the same vote, so a second switch would only offer the two settings nobody wants, to be canvassed and never told or told about a vote you were never invited to. `announceMotmResult` is silent when nobody voted: there is a decision document either way, but "nobody voted" is not news worth a buzz.
- **App admins hear both halves whether or not they played.** They are the only people who can do anything about a wrong answer — the bonus reaches a rating through a replay, so a correction is theirs — which is the same standing that puts `newPlayer` in front of them, and it is still behind the `motm` switch so an admin who wants none of it says so in one place. Both ends dedupe with a `Set`, because `sendPush` resolves one recipient per uid and an admin who played is in both lists. Only the lineup can actually *vote*: the rules check the team sheet at both ends, so an admin who sat one out is being told, not asked, and `MotmPanel` already shows them the turnout with no ballot on it.
- The announcement is **reported and swallowed** inside `closeMotmVote`, unlike every write above it. By the time it sends, the decision is written and the window is gone, so the sweep will never bring that game round again — and the caller reads the return value to decide whether to replay the ladder. A throw would cost the winner their bonus over a notification that failed, and log a misleading "could not count" for a vote counted correctly. `closeMotmVoting` declares `EMAIL_SECRETS` for the same reason the two confirmation entry points do.
- `availability` is also the only kind that can fire several times an evening, which is what the shared `game-{id}` tag is for — a run of late changes of heart replaces itself on the lock screen rather than stacking. `getAvailabilityChange` in `shared/game.ts` is what keeps it honest: `setResponse` rewrites the whole document, so a note edit and an admin confirming an extra both arrive at `onResponseWrite` looking exactly like an answer, and only a moved `status` is news.
- **Email is a fallback, never a second channel.** `sendPush` emails exactly the people it reached no device for — none registered, or every token dead — and never somebody a push got to, per person rather than per token. The per-kind preferences gate it first, so an opt-out can't be routed around by turning off push; `emailFallback` on the profile switches the channel off entirely. `canEmail` is that rule in one place.
- Nothing is composed for email. `buildEmail` takes the `PushPayload` the trigger already built, so there is one wording per notification and no second copy to keep in step.
- Addresses live in **Firebase Auth only** and are read there with the Admin SDK. `users/{uid}` is readable by every signed-in player, so a mirrored address would be a group-wide address book — see `scripts/stripUserEmails.ts`. The admin screen learns whether somebody _has_ an address, never what it is.
- The transport is Resend, behind a `RESEND_API_KEY` secret with `EMAIL_FROM`/`APP_URL` in `backend/.env`. Unconfigured it is inert, and in the emulator it logs instead of sending. **The secret must exist in Secret Manager or every functions deploy fails** — CI deploys non-interactively, where a missing secret is an error rather than a prompt. Locally it is read from `backend/.secret.local`, committed with a placeholder: the emulator resolves every declared secret when it starts a runtime worker and asks Secret Manager when nothing overrides it, which on a machine with a login is a wasted round trip and in CI is an access failure logged beside a trigger that worked. The value is never used — `sendEmail` returns on `FUNCTIONS_EMULATOR` before reading it — so a real key there would be a real key on disk for nothing.
- **A tap on a notification routes the window that is already open rather than loading a page into it.** The worker focuses that window **first**, then hands it the URL over a `MessageChannel`; `useNotificationRoute` acknowledges and calls `router.push`. `client.navigate()` is only the fallback for a window that doesn't answer within `ROUTE_ACK_MS` — an older bundle with no listener, or a page whose JS has died, both of which genuinely want a reload. Focusing *second* is what the old order got wrong: iOS laid the incoming page out against the viewport the web view had while it was still backgrounded and never remeasured, so `position: fixed` kept resolving against a rectangle that was no longer the viewport and the top bar and tab bar scrolled away with the content. It needed a window to have survived in the background to reuse, which is why it hit some taps and not others. Two smaller things are load-bearing: `navigator.serviceWorker.startMessages()`, because `addEventListener` alone leaves the worker's messages queued where assigning `onmessage` would have started delivery; and the reload when only the query moved, because `router.push` to the path you are already on re-renders without remounting and `useRespondIntent` reads `?respond=in` once on mount.
- The admin debug screen (`/debug`) has two send paths, both app-admin-only: `sendTestPush` always sends to `request.auth.uid` and nobody else — deliberately, so it can't become a way to notify somebody else. `sendTestEmail` is the one exception, emailing a chosen set of real accounts through the real `sendEmail` transport; it shares `buildTestPayload`/`buildTestContext` with `sendTestPush` so the two can't drift into testing different copy, and it skips the per-kind preference (an admin picking a person and a kind is a one-off decision, not the automated send that preference silences) while still honouring `emailFallback` and requiring a verified address.
- `users/{uid}.client` records the platform somebody last signed in on and the last time they opened it installed. Self-written on every sign-in. `lastStandaloneAt` only moves **forward** — opening a link in a browser tab must not read as an uninstall, and an uninstall can't be observed at all.
- `users/{uid}.lastSeenAt` is **arrival-only**, and that is the whole design (`shared/visit.ts`). It moves when the app loads in the foreground and on every return to it, never on a timer — a heartbeat from a suspended installed app or a tab behind forty others would keep the stamp fresh for exactly the person it exists to surface, and no interval can tell an idle visible window from a present one without tracking input. `upsertUserDoc` seeds it on the load, `useLastSeen` owns every move after that, and the two are exhaustive: a page either loads on screen or reaches it through a `visibilitychange`. The consequence to accept is that a long session records when it *began*. `/admin/activity` is the one screen that reads it, bucketed by `visitRecency` into weeks rather than calendar months because a season is a weekly slot — a week is one game. It stays separate from `/admin/notifications` on purpose: "we can't reach them" is a device or a preference and is fixable from that screen, while "they stopped coming" is a conversation. The same reasoning is why `upsertUserDoc` now runs once per sign-in rather than on every token refresh — a forced refresh every ten minutes was rewriting the whole profile, and stamping a visit, from a tab nobody had looked at in a week.
- Push tokens stay private to their owner: a token is a capability to push to that device. The admin screen gets them through the `getPushDevices` callable, which strips the token and returns platform, browser and registration date. Don't relax the rule instead — it would hand every admin a working send-anything credential for every phone in the group.
- **Who is following a game is visible to app admins only, and through a callable for the same reason.** `availability` is the one kind whose audience isn't already on screen — every other kind goes to the roster, the people who answered, or the admins, all of which are readable — so `getGameWatchers` answers "who hears if I move kick-off" on the game page itself. The rule stays shut: `watchers/{uid}` is still readable by nobody but its owner, season admins and app admins included, and the rules suite pins both the document and the collection. Loosening it would publish the same list to every signed-in client rather than to the one screen that asked.

## Error reporting

- Both halves report to **one Sentry project** — a failed write and the trigger that should have followed it belong in the same inbox. Unconfigured it is inert, like the email transport: a blank DSN sends nothing and changes no behaviour.
- **Nothing is reported from a local run.** The frontend reports only from a build Vercel made (`NEXT_PUBLIC_VERCEL_ENV`, which `next dev` does not set) — an emulator-only check used to read as this rule but let `dev:live` through, and `next dev`'s HMR throws from the webpack runtime on every hot update, so the inbox filled with `localhost:3000`. Set `NEXT_PUBLIC_VERCEL_ENV` for one run to report on purpose. The backend checks `FIRESTORE_EMULATOR_HOST`, which is wider than `FUNCTIONS_EMULATOR` on purpose because `pnpm test:backend` imports the handlers straight into jest and would otherwise report its own deliberately-provoked failures.
- **`ErrorBoundary` reloads the page once on a crash**, flushing the report first — `captureErrorAndFlush` rather than `captureError`, because the SDK's queue lives in the page and a reload would take the one report that explains it. A missing module from a chunk that never arrived is the common case on a phone and only a refetch fixes it. The mark is a timestamp in `sessionStorage`: a second crash within seconds means the reload was not the answer and the fallback stays put, while a crash an hour later is a fresh episode. Storage that throws counts as "can't record it", so it does not reload — an unguarded retry on a deterministic crash is a loop.
- A new service worker **waits** rather than calling `skipWaiting()`, which is the upstream half of that same crash. Activating deletes the previous version's caches out from under a page still running it, so a deploy landing mid-session left the old build with its chunks uncached and — once Vercel aged them out — unfetchable. `useServiceWorkerUpdate` offers the waiting build, posts `SKIP_WAITING` when accepted, and reloads on `controllerchange`. Two things are load-bearing there: **only reload if the page already had a controller** (a first install claims an uncontrolled page and would otherwise refresh every first visit), and re-check `registration.update()` on returning to the foreground, because an installed PWA can go weeks inside one document without ever requesting `/sw.js` again.
- **Only the uid identifies a person**, never a name or an address — the same line `forget-player` draws. `sendDefaultPii` is off, and Session Replay is off because it would record a roster of real names.
- `instrument()` wraps **every** exported function. It reports and **rethrows** — background triggers need the throw to be retried and callables need it to answer the client, so telemetry must never change what a function does. An `HttpsError` is skipped: it is a decision the code made, and an inbox full of the authorization layer working correctly is one nobody opens.
- The `catch` blocks that deliberately swallow an error to keep a sweep going go through `reportError`, which logs **and** reports. Those are the failures GCP genuinely cannot see, and the ones that can repeat weekly with nothing to show for it.
- Every scheduled sweep goes through `instrumentSchedule`, which **check-ins** to a Sentry cron monitor as well as reporting errors. A sweep that throws reports an error; a sweep that never runs at all reports nothing, and that silence is indistinguishable from a quiet week — the check-in is what makes absence visible. The expected schedule is upserted from the code beside the `onSchedule` that implements it, so a dashboard can't drift from reality.
- `auditGameCounts` (daily) is the third case neither of the above catches: **state that is quietly wrong**. `counts` and `atRisk` come from a background trigger, and a trigger that exhausts its retries leaves no trace anywhere — nothing threw where anybody was looking, and the sweep that *did* run was fine. It re-derives the answer with `findCountsDrift` and **reports without repairing**: `recountGames` is the repair, and fixing this nightly would clear the symptom while the trigger carried on failing. One report per sweep, not per game — a broken trigger takes out every game at once. Scoped to upcoming games in active seasons; drift on a game already played changes nothing.
- Tracing is off and tree-shaken out (`webpack.treeshake.removeTracing`). Turning it back on means deleting that line — and costs 28 kB gzipped on the shared bundle.
- `/me` shows the commit this bundle was built from, to **everybody** rather than just admins — "the app is broken" and "which build are you on" are the same question, and a phone stuck on an old build is the shape of failure this app has actually had. `lib/build.ts` reads it from `NEXT_PUBLIC_BUILD_SHA`, mapped in `next.config.js` from Vercel's `VERCEL_GIT_COMMIT_SHA` rather than relied on from Vercel's auto-exposed copy, which depends on a dashboard setting the repo can't see. **`sentryOptions` sets no `release`** — the build plugin already injects one from the same sha, and a second one that disagreed would detach the source maps and minify every stack trace.
- `/debug` can **break things on purpose** — four browser paths and the `throwTestError` callable — because a reporting pipeline looks identical working and broken. Each button takes a genuinely different route (React swallows render errors, ignores throws from event handlers, and neither is how a rejected write surfaces), so one passing says nothing about the others. `httpsError` is the one that must produce **no** Sentry issue. They go down the real paths rather than calling `captureException` directly: a trigger with its own private route would still pass with `instrument` deleted from every function.

## Members vs extras

- A **member** is on `season.memberUids`. Members have no cap and always rank first.
- An **extra** is any other signed-in user. Extras can respond to any game but always sort below members and carry a `confirmed` flag (auto-set in signup order by the trigger, overridable by a season admin).
- `role` is snapshotted on the response document and validated in security rules against actual membership at write time.

## Conventions

- Arrow-function components with a `default export` at the bottom. Props typed inline in the destructuring position — no `React.FC`, no separate `Props` interface unless it's genuinely shared.
- `import type` is enforced by eslint (`@typescript-eslint/consistent-type-imports`).
- Use the `classNames(...)` helper in `frontend/lib/utils/reactHelper.ts` for conditional classes — not clsx/cva.
- Prettier: tabs, width 4, printWidth 120, single quotes (including JSX), `arrowParens: avoid`.
- Pure domain logic (dates, game state, sorting) belongs in `shared/` with unit tests — not in components.
