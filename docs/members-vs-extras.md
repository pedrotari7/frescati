# Members vs extras

Part of Frescati's CLAUDE.md context. See the root `CLAUDE.md` for the app overview.

- A **member** is on `season.memberUids`. Members have no cap and always rank first.
- An **extra** is any other signed-in user. Extras can respond to any game but always sort below members and carry a `confirmed` flag (auto-set in signup order by the trigger, overridable by a season admin).
- `role` is snapshotted on the response document and validated in security rules against actual membership at write time.
- **An extra's In is the one answer that does nothing on its own, so the app has to say so out loud.** `playing` is `membersIn + extrasConfirmed`, which means tapping In as an extra moves no number on any screen until an admin nods, every other answer is its own receipt, and this one used to be a permanent grey line that read the same before and after the tap, with the real state in a pill beside their name on a roster they had to go and find. `getExtraSpot` in `shared/game.ts` is the state (`pending` | `confirmed` | nothing to say) and `ExtraSpotNote` draws it under the buttons on both screens the tap happens on. It reads the **response**, never the viewer's role: `role` is snapshotted at write time and is what the tally counts, so somebody added to `memberUids` after answering is genuinely still queued as an extra on that game. `isExtra` is only for the case with no document to read a role from, explaining what the button will do.
- **The confirmation is what shows on the season's home screen**, because that is where somebody checks whether anything happened: the hero's note turns green, and the row's pill goes from an amber `Spot pending` to `You're in`. Once the game is behind us a never-confirmed extra reads `No spot`, nobody confirms a spot for a game that has been played, and an amber pill on a dead question invites a wait that is already over. `getAwaitingSpotCount` puts the same fact on the headcount strip for everybody, in `pending`: it is the one item there that is a request rather than a report, and the only prompt an admin gets that somebody is waiting.
- **Nothing notifies them.** `getAvailabilityChange` returns `null` when only `confirmOverride` moved, deliberately, so a confirmation doesn't read to watchers as an answer changing, and no push is aimed at the extra either. The screens above are the whole channel.
